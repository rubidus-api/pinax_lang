# 17 ABI 와 호환

> **먼저 알아야 할 것**: 14장. 호스트 밑의 Pinax 를 올릴 때 찾아보는 장이다.
>
> **이 장이 답하는 물음**
>
> - 한 릴리스의 헤더로 호스트를 컴파일했다. 뒤의 라이브러리와도 도는가?
> - 무엇을 링크하고, 시작할 때 맞는 라이브러리인지 어떻게 보는가?
> - 콜백에서 무엇을 불러도 되는가?

## 17.1 번호 넷

| **번호** | **말하는 것** | **바뀌는 때** |
|---|---|---|
| `PINAX_VERSION_MAJOR` `_MINOR` `_PATCH` | 릴리스 | 릴리스마다 |
| `PINAX_FORMAT` | 소스, 상, 공유 파일 | 그 형식 하나가 깨지게 바뀔 때 |
| 컨테이너 판 | `pinax_load_bytecode` 가 읽는 것(내부) | 컨테이너가 깨지게 바뀔 때 |
| `PINAX_ABI` | `pinax.h`, `pinax_host.h`, `pinax_loop.h` 의 바이너리 인터페이스 | 옛 헤더로 컴파일한 호스트가 새 라이브러리에서 잘못 돌 수 있을 때 |

릴리스 N 으로 컴파일한 호스트는 다시 컴파일하지 않아도 같은 `PINAX_ABI` 의 뒤 라이브러리와 모두 돈다. `PINAX_ABI` 를 올리는 릴리스는 노트의 “Breaking” 에 그렇다고 적고, 호스트가 바꿀 것을 함께 적는다.

## 17.2 시작할 때의 검사

```c
if (!PINAX_ABI_OK()) {
    /* 이 호스트가 컴파일된 라이브러리가 아니다 */
}
```

`PINAX_ABI_OK()` 는 라이브러리에 `pinax_abi()` 와 `pinax_version()` 을 묻는다. ABI 는 헤더와 같고, 판은 헤더 이상이어야 한다(새것을 쓰는 호스트는 그것이 있는 라이브러리가 있어야 한다).

## 17.3 깨지지 않는 것과 깨지는 것

| **깨지지 않는다** | **깨진다(`PINAX_ABI` 가 오른다)** |
|---|---|
| 새 함수, 새 플래그 비트, 범위 끝의 새 오류 코드, `struct_size` 로 시작하는 구조체 끝의 새 칸, 규칙이 위반이라 부르는 호출의 거절(아래 표) | 함수의 삭제나 이름 바꿈, 인자나 결과의 타입 바꿈, 칸의 이동·삭제·타입 바꿈, `struct_size` 없는 구조체의 크기 바꿈, 열거값이나 플래그 비트의 바꿈 |

오류 코드와 플래그는 모두 헤더에 값이 적혀 있다. 라이브러리가 모르는 플래그 비트는 `PINAX_ERR_ARGUMENT` 로 거절하므로, 뒤의 헤더로 빌드한 호스트는 그것을 곧 안다. `struct_size` 로 시작하는 구조체는 헤더가 적은 크기들로만 받고, 그 사이의 크기는 받지 않는다. `pinax_stats_get` 은 모르는 크기에 `struct_size` 0 으로 답한다. `./nob abi` 는 헤더와 라이브러리를 지난 릴리스의 것과 여섯 대상에서 비교하고, 바뀐 것이 어긴 규칙의 이름을 댄다.

## 17.4 무엇을 링크하는가

| **꼴** | **링크 줄** |
|---|---|
| 핵, 정적 | `cc host.c build/native/release/libpinax.a -lm` |
| 호스트 모듈과 함께 | `... release/libpinax_host.a release/libpinax.a -lm -pthread` |
| `sqlite` 와 함께 | `... release/libpinax_sqlite.a release/libpinax_host.a release/libpinax.a -lm -pthread` |
| 한 파일 | `cc -std=c23 -c pinax.c` 뒤에 `pinax.o` 를 링크 |
| 공유(리눅스) | `./nob shared`: `cc host.c -Lbuild/native/shared -lpinax`(soname `libpinax.so.1`) |
| 공유(윈도) | `-DPINAX_SHARED` 로 컴파일하고 `libpinax.dll.a` 나 `pinax.def` 를 링크, `pinax.dll` 을 함께 낸다 |

호스트가 링크하는 것에서는 공개 이름(`pinax_`)만 전역이고, 핵의 자기 이름은 `pinax__` 다. 안의 proven_c_lib 와 SQLite 는 감춰져 있어서, 호스트가 자기 것을 함께 링크해도 된다. 라이브러리는 GCC 나 Clang 으로 빌드한다. MSVC 로 컴파일한 호스트는 DLL 을 쓴다.

> **흔한 오해: 내보낸 코드를 공유 라이브러리에 링크한다**
>
> `pnx export-c` 의 C 는 릴리스마다 바뀌는 핵의 자기 함수(`pinax__...`)를 부른다. 내보낸 릴리스의 정적 아카이브나 `pinax.c` 와 링크하고, 공유 라이브러리와는 링크하지 않는다.

상과 내보낸 코드는 같은 배치에서만 쓴다. 다른 빌드의 것은 거절한다(`PINAX_ERR_FORMAT`, 또는 표를 붙이지 않는다).

## 17.5 콜백이 불러도 되는 것

| **안에서** | **상태에 불러도 되는 것** |
|---|---|
| 호스트 프로시저 | `pinax_call_...`, `PINAX_FIND_NESTED` 를 준 `pinax_find`, `pinax_global_find`, 그렇게 찾은 낱말의 `pinax_run`, 핸들 함수, 읽는 함수 |
| barrier, trace, task fault, `diag` 함수 | 읽는 함수: `pinax_error_text`, `pinax_needed`, `pinax_fault_local`, `pinax_task_faults`, `pinax_eval_count`, `pinax_eval_value`, `pinax_word_at`, `pinax_image_size`, `pinax_share_size`, `pinax_stats_get` |
| 핸들 타입의 close 함수 | `pinax_handle_get`, `pinax_handle_release` |
| `extern` 해결 함수 | 아무것도 없다 |

그 밖의 호출은 거절한다(`PINAX_ERR_STATE`, 0, `NULL`, 또는 아무것도 하지 않음). 오류 글은 그 콜백의 이름을 댄다. `pinax_close` 는 어느 콜백에서도 부르지 않는다.

> **문답**
>
> **물음. 믿지 못하는 스크립트에 C 함수 몇 개만 부르게 하려면?**
>
> 답. 타입 있는 해결 함수(`pinax_set_typed_resolver`)를 둔다. 함수마다 C 배치를 함께 답하고, 다르게 선언한 스크립트는 적재에서 거절된다. 어떤 인자 값에도 안전한 함수만 준다.

## 17.6 호스트를 올릴 때

1. 새 릴리스를 빌드하고, 쓰는 컴파일러로 `./nob contract` 를 돌린다.
2. 릴리스 노트의 “Breaking” 을 읽는다. `PINAX_ABI` 가 바뀌었으면 호스트를 다시 컴파일하고 적힌 대로 고친다.
3. 시작할 때 `PINAX_ABI_OK()` 를 그대로 둔다.
4. 새 릴리스로 C 를 다시 내보낸다( `pnx export-c` ). 옛 릴리스의 상은 열지 않는다.

> **정리**
>
> - `PINAX_ABI` 는 바이너리 인터페이스의 번호다. 같은 번호 안에서 옛 호스트는 새 라이브러리와 돈다.
> - `PINAX_ABI_OK()` 가 시작할 때 라이브러리를 본다.
> - `release/` 를 링크한다. 전역은 `pinax_` 이름뿐이고, 안의 proven 과 SQLite 는 감춰져 있다.
> - 콜백은 표가 허락하는 것만 부른다. 나머지는 거절된다.
> - 내보낸 코드와 상은 한 빌드의 것이다.
