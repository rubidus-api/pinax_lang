11 Text and binary formats

Builds on: Chapter 5 (views, buffers), chapter 7 (records), chapter 8 (failures).

Questions this chapter answers

  • How are CSV and JSON read and written without building a tree?
  • How is a record sent as bytes and read back?
  • Where are hashes and conversions like Base64?

Pinax has no heap, so it does not read JSON into a tree of objects. Instead it reads in one direction: one token, one field at a time. It writes straight into a buffer. Fitting records is done by code made from the record’s declaration.

11.1 CSV and JSON#

csv.unpack reads one line into the fields of a record in order, and json.pack writes a record as an object keyed by field names.

11-csv-to-json.pnx

use io .
use csv .
use json .
use str .
rem Read CSV rows into records, write them out as JSON.
record city
  name str 16
  people i32
  capital bool
end
list cities city 8
buffer out 512
def read_rows input str or fail do
  input str.lines do to line
    cities len to before
    cities add_row or_fail to c
    line c csv.unpack or_else to e before cities truncate  args "bad row: " line . cat io.println  "" end drop
  end each
end
def to_json or fail do
  out json.begin_array or_fail
  cities do to c c out json.pack or_else to e end end each
  out json.end_array or_fail
end
text END
Seoul,9411000,true
Busan,3349000,false
Daejeon,lots,false
END
read_rows or_else to e end
to_json or_else to e e err_text io.println end
out contents io.println

Output

$ pnx 11-csv-to-json.pnx
bad row: Daejeon,lots,false
[{"name":"Seoul","people":9411000,"capital":true},{"name":"Busan","people":3349000,"capital":false}]

The row is added first; when unpack fails, before cities truncate takes it back by cutting the list to the length it had before.

Common mistake: Taking the last row of a list of records off with pop

Lists of records have no pop (only lists of values do). The last row is taken back with truncate. When an index or a field holds rows of that list, truncate is refused too; then check before adding.

11-pop-records.pnx

record city
  name str 16
end
list cities city 4
def undo do cities pop or_else to e cities none end drop end

Refused

$ pnx 11-pop-records.pnx
11-pop-records.pnx:5:20: pop takes from a list of values; a list of records has no pop

Reading JSON by tokens picks out just what is needed, at any depth. json.next gives the kind of the token, a view of its value, and the rest.

11-json-read.pnx

use io .
use json .
use str .
rem Sum every number in a JSON text, at any depth, without building a tree.
def sum_numbers s str gives int do
  0 to total
  s to rest
  loop
    rest json.next or_else to e break . end to rest to value to kind
    kind json.number eq if total value str.to_int or_else to e 0 end add to total end
  end
  total
end
text END
{"a": 1, "b": [2, 3, {"c": 4}], "d": {"e": [5]}, "f": "6"}
END
sum_numbers str.to_str io.println

Output

$ pnx 11-json-read.pnx
15

Look at the three things json.next gives, one token at a time. s json.next gives (kind int, value str, rest str): the kind of the token, its text (a view), and the text left after it. Giving what is left to json.next again, over and over, walks the whole text once from the front. At the end of the text json.next fails, and that failure ends the loop.

11-json-tokens.pnx

use io .
use json .
rem The tokens of a JSON text, one at a time: what json.next gives for each.
def kind_name k int gives str do       rem module constants are compared with eq, not case
  k json.object eq if "object" return end
  k json.object_end eq if "object end" return end
  k json.array eq if "array" return end
  k json.array_end eq if "array end" return end
  k json.key eq if "key" return end
  k json.string eq if "string" return end
  k json.number eq if "number" return end
  "other"
end
def show_tokens s str do
  s to rest
  loop
    rest json.next or_else to e break . end to rest to value to kind   rem fails at the end: leave the loop
    args kind kind_name " [" value "]" . cat io.println
  end
end
"{\"name\": \"Pinax\", \"sizes\": [8, 16]}" show_tokens

Output

$ pnx 11-json-tokens.pnx
object [{]
key [name]
string [Pinax]
key [sizes]
array [[]
number [8]
number [16]
array end []]
object end [}]
TokenStack after itWhat happened
rest json.nextjson.object "{" …Reads {: kind json.object; what is left is "name": ….
or_else to e break endjson.object "{" …It did not fail, so the body is skipped.
to rest to value to kind—The three go into names; the first written, rest, takes the top value.

A kind is a module constant like json.object, so it is compared with eq, not match (chapter 4). Only the work for each kind has to be chosen, so the values needed can be picked out at any depth; 11-json-read.pnx added up the json.number tokens only.

A value of no interest is skipped in one go with json.skip an object or an array is skipped with everything inside it, so there is no depth to count. The kinds are the constants json.object json.object_end json.array json.array_end json.key json.string json.number json.boolean json.null. The other way round, one object fills a row of a record with json.unpack: the row is written only when every field fits, else it fails.

11-json-skip.pnx

use io .
use str .
use json .
record point
  x int
  y int
end
array pts point 1
def demo or fail do
  "{\"tags\": [1, [2, 3]], \"x\": 4}" json.next or_fail to rest to v to k   rem the {
  rest json.next or_fail to rest to v to k                                   rem the key tags
  rest json.skip or_fail to rest                                           rem the whole array, however deep
  rest json.next or_fail to rest to v to k                                   rem the key x
  rest json.next or_fail to rest to v to k                                   rem 4
  args "after the skip: " v ", a number? " k json.number eq . cat io.println
  "{\"x\": 7, \"y\": 9}" 0 pts idx json.unpack or_fail drop
  args "unpacked " 0 pts idx point.x " " 0 pts idx point.y . cat io.println
  "{\"x\": true}" 0 pts idx json.unpack or_else to e args "unpack failed: " e err_text . cat io.println "" end drop
end
demo or_else to e e err_text io.println end

Output

$ pnx 11-json-skip.pnx
after the skip: 4, a number? true
unpacked 7 9
unpack failed: format

CSV is written one field at a time. csv.put appends text (quoted when it holds a comma, a quote or a line break), csv.put_int csv.put_dec csv.put_bool numbers and booleans, and csv.end_line the end of the line; the commas between fields are the procedures’ business. One row of a record as one line is csv.pack.

11-csv-write.pnx

use io .
use csv .
buffer out 64
def demo or fail do
  "kim" out csv.put or_fail  3 out csv.put_int or_fail  true out csv.put_bool or_fail  out csv.end_line or_fail
  "a, b" out csv.put or_fail  2.50 out csv.put_dec or_fail  out csv.end_line or_fail
  out contents io.print
end
demo or_else to e e err_text io.println end

Output

$ pnx 11-csv-write.pnx
kim,3,true
"a, b",2.50

11.2 Paths, settings files and Markdown#

Reading by tokens suits a stream. When the text is a document and one value is wanted, json.at takes a path: names joined by dots and indexes in brackets, user.langs[1]. It gives the kind and the text of the value; an object or an array comes whole, as written, so it can be asked again. A missing value is err.not_found, so or_else is the place for a default. json.valid says whether a text is JSON at all, and json.minify and json.pretty write it into a buffer without its blanks, or one value to a line.

11-json-path.pnx

use io .
use json .
def main or fail do
  text END
{"user": {"name": "kim", "langs": ["ko", "en"]}, "visits": 12}
END
  to doc
  "user.name" doc json.at or_fail io.println drop      rem the value at a path
  "user.langs[1]" doc json.at or_fail io.println drop  rem an index in brackets
  "visits" doc json.at or_fail drop json.number eq to is_number
  args "visits is a number: " is_number . cat io.println
  "user.email" doc json.at or_else to e args "no email: " e err_text . cat io.println 0 "" end drop drop
end
main or_else to e e err_text io.println end

Output

$ pnx 11-json-path.pnx
kim
en
visits is a number: true
no email: not_found

TOML, the format of settings files, is read the same way by the module toml: toml.at with a path (server.ports[1], backend[1].url for the second [[backend]]), or toml.next for every statement in order, headers included. A value is given as written: a string without its quotes (and with its escapes decoded), a number as its text. toml.check judges a whole file before the program trusts it: a key given twice, a table opened twice, an integer that does not fit 64 bits or a date that does not exist is err.format. toml.set changes one value by its path (or adds the key at the end of its table) and toml.remove drops a key, each into a buffer, and everything else in the file, comments included, stays as it was.

11-toml-config.pnx

use io .
use toml .
def main or fail do
  text END
name = "shop"            # the name of the service
[server]
host = "0.0.0.0"
ports = [8080, 8443]
[[backend]]
url = "http://a.local"
[[backend]]
url = "http://b.local"
END
  to conf
  "server.host" conf toml.at or_fail io.println drop
  "server.ports[1]" conf toml.at or_fail io.println drop
  "backend[1].url" conf toml.at or_fail io.println drop
  conf toml.valid to fine
  args "valid: " fine . cat io.println
end
main or_else to e e err_text io.println end

Output

$ pnx 11-toml-config.pnx
0.0.0.0
8443
http://b.local
valid: true

Markdown becomes HTML with md.html: headings, paragraphs, emphasis, code, links, lists, quotes and tables. Raw HTML in the text is not passed on and a link to javascript: is written as plain text, so the result is safe to put in a page. md.next reads a document a block at a time, and md.inline writes one line without a paragraph around it. Both are a subset of CommonMark (standard 16.12 says which).

11-md-html.pnx

use io .
use md .
buffer page 1024
def main or fail do
  text END
## Notes

A line with *emphasis*, `code` and a [link](https://example.org).
Raw <b>tags</b> stay text.

1. first
2. second
END
  to doc
  doc page md.html or_fail
  page contents io.println
end
main or_else to e e err_text io.println end

Output

$ pnx 11-md-html.pnx
<h2>Notes</h2>
<p>A line with <em>emphasis</em>, <code>code</code> and a <a href="https://example.org">link</a>.
Raw &lt;b&gt;tags&lt;/b&gt; stay text.</p>
<ol>
<li>first</li>
<li>second</li>
</ol>

When the loop is all you want, walk the pieces as a rail: s json.items gives the elements of an array, s json.members the members of an object (path s json.items_at for the one a path names), s toml.items the statements of a TOML text and s md.blocks the blocks of Markdown. Each turn gives several values, bound by do to v to k to key (the last pushed first), and the rail is open and lazy, so head 2 reads no more than two. A text that is damaged after some good elements fails at that turn, so the loop is followed by a guard.

11-json-rails.pnx

use io .
use str .
use json .
def total s str gives int or fail do                  rem the numbers of an array; the others are passed over
  0 to acc
  s json.items do to v to k
    k json.number eq if v str.to_int or_fail acc add to acc end
  end each or_fail
  acc
end
def show s str or fail do
  s json.members do to v to k to key                   rem the last pushed first: the value, the kind, the key
    args key " (" k ") = " v . cat io.println
  end each or_fail
end
"[1, 2, \"x\", 3, [4, 5]]" total or_else to e -1 end str.to_str io.println
"{\"a\": 1, \"b\": [1,2], \"c\": {\"d\": null}}" show or_else to e "bad" io.println end
def langs s str or fail do                             rem a path names the array
  "user.langs" s json.items_at do to v to k v io.println end each or_fail
end
"{\"user\": {\"langs\": [\"lua\", \"c\"]}}" langs or_else to e "bad" io.println end
"[1, 2" total or_else to e e err_text io.println 0 end drop      rem damaged after two good elements
"[1,2,3,4,5]" json.items head 2 do to v to k v io.println end each or_else to e end   rem lazy: the text is read no further

Output

$ pnx 11-json-rails.pnx
6
a (7) = 1
b (3) = [1,2]
c (1) = {"d": null}
lua
c
format
1
2

Q&A

Q. Is there a tree after json.at?

A. No. Each call reads the text again from the front up to the value it wants, so for many values from one large document the token procedures, which read it once, are cheaper.

11.3 Bytes#

The module bytes writes and reads fixed widths in a given byte order. With big_endian in a record, bytes.pack writes the most significant byte first. A varint field writes small numbers in few bytes.

11-binary.pnx

use io .
use bytes .
use encode .
use hash .
use fmt .
record header
  big_endian
  magic u32
  version u16
  length varint
end
array headers header 2
buffer wire 32
buffer hex 64
def demo or fail do
  0 headers idx to h
  0x50494e58 u32 h to header.magic           rem "PINX"
  1 u16 h to header.version
  300 h to header.length
  h wire bytes.pack or_fail
  wire contents hex encode.hex_encode or_fail
  args "bytes: " hex contents ", crc32: " wire contents hash.crc32 fmt.hex . cat io.println
  1 headers idx to back
  wire contents back bytes.unpack or_fail drop
  args "read back: version " back header.version ", length " back header.length . cat io.println
end
demo or_else to e e err_text io.println end

Output

$ pnx 11-binary.pnx
bytes: 50494e580001ac02, crc32: 31d80bed
read back: version 1, length 300

The writing procedures (pack, put_…, encode.…_encode) fail when the buffer is full, so a guard always follows them.

11-pack-unguarded.pnx

use json .
record point
  x int
  y int
end
list points point 2
buffer out 64
def write p points do p out json.pack end   rem pack fails when the buffer is full: no guard

Refused

$ pnx 11-pack-unguarded.pnx
11-pack-unguarded.pnx:8:39: a procedure that can fail is followed by or_fail, or_return or or_else

Q&A

Q. Does the record lie in memory in big-endian order too?

A. No. big_endian sets only the order of the bytes that pack and unpack use. The layout in memory is the processor’s, and a script cannot see it.

11.4 Other conversions#

fmt turns numbers into hexadecimal, binary and zero-padded text. hash gives CRC-32, FNV-1a and SipHash; encode gives Base64, hexadecimal and URL percent-encoding. Procedures that write their results into a buffer fail when the buffer is full. The full lists are in clause 16 of the standard.

A hash takes text and gives an int. hash.crc32 is a checksum; hash.fnv1a and hash.hash64 mix keys. How many bytes one row of a record becomes under bytes.pack is told in advance by bytes.packed_size, which helps in sizing a buffer.

11-hash.pnx

use io .
use fmt .
use hash .
use bytes .
record pair
  a u16
  b int
end
array pairs pair 1
def demo do
  args "crc32 " "pinax" hash.crc32 fmt.hex ", fnv1a " "pinax" hash.fnv1a fmt.hex . cat io.println
  args "a pair packs into " 0 pairs idx bytes.packed_size " bytes" . cat io.println
end
demo

Output

$ pnx 11-hash.pnx
crc32 19afea99, fnv1a 131b946615bc7b35
a pair packs into 10 bytes

Q&A

Q. Can the JSON writer indent, or add line breaks?

A. The writing procedures of json append one line. For a layout for people, give the text to json.pretty, which writes it with a member to a line.

Summary

  • json.next and csv.fields read one token, one field at a time; no tree is built (standard 16.8, 16.9).
  • pack writes into a buffer; unpack writes into the row only when all is right (16.5, 16.8, 16.9).
  • json.at and toml.at find a value by a path; md.html makes safe HTML from Markdown (16.8, 16.11, 16.12).
  • big_endian sets only the byte order (16.5).
  • Lists of records have no pop (15.3).
